# PostgreSQL Best Practices

Based on the PostgreSQL Official Docs and the PostgreSQL Wiki "Don't Do This".

> Worked examples live in the `postgres-reference` skill (`references/universal.md`).

---

## 1. Data Types — Choose Correctly

The most impactful schema decision. Wrong types cause bugs, waste space, and prevent indexing.

- **TEXT, not VARCHAR/CHAR.** TEXT, VARCHAR, and VARCHAR(n) share the same `varlena` storage; VARCHAR(n) only adds a length CHECK. Zero performance benefit. Use TEXT + an explicit CHECK only for a genuine business rule. CHAR(n) pads with spaces (wastes storage; `'U'::CHAR(2)` stores `'U '` — trailing spaces present in storage, ignored in comparison).

- **TIMESTAMPTZ, not TIMESTAMP.** Bare `TIMESTAMP` has no timezone context — if the server moves UTC→US-East all values silently shift. `TIMESTAMPTZ` stores UTC internally, displays in session timezone, never ambiguous.

- **NUMERIC(p,s), not FLOAT/MONEY** for financial data. FLOAT is binary-approximate: `0.1::FLOAT + 0.2::FLOAT = 0.3::FLOAT` is FALSE (NUMERIC is TRUE). MONEY is locale-dependent (`lc_monetary`) and hard to convert/export. `p` = total digits, `s` = decimal places.

- **IDENTITY, not SERIAL.** SQL standard; sequence is tightly bound to the column. `GENERATED ALWAYS AS IDENTITY` blocks accidental explicit ids (prevents PK collisions); `GENERATED BY DEFAULT` allows explicit ids (useful for imports). SERIAL creates a loose sequence that can desync.

- **BOOLEAN** for true/false (not integer flags). **UUID** for external ids/tokens (`DEFAULT gen_random_uuid()`, built-in since PG 13; PG 18+ prefer `uuidv7()` — time-sortable, index-friendly). **INTERVAL** for durations (native timestamp arithmetic). Use the smallest fitting integer: `SMALLINT` (2B), `INTEGER` (4B), `BIGINT` (8B) — use BIGINT for PKs on high-volume tables.

### Data Type Decision Table

| Data | Type | Why |
|------|------|-----|
| Free text | `TEXT` | No perf difference from VARCHAR |
| Date + time | `TIMESTAMPTZ` | Unambiguous timezone handling |
| Money / financial | `NUMERIC(p, s)` | Exact decimal arithmetic |
| True/false | `BOOLEAN` | Self-documenting, proper semantics |
| Auto-increment PK | `BIGINT GENERATED ALWAYS AS IDENTITY` | SQL standard, overflow-proof |
| External IDs / tokens | `UUID` | Globally unique, no sequence bottleneck |
| Duration | `INTERVAL` | Native arithmetic with timestamps |
| IP addresses | `INET` / `CIDR` | Subnet operations, indexable |
| Coordinates | `POINT` / PostGIS `GEOMETRY` | Native distance/containment ops |
| Structured semi-data | `JSONB` | Indexable, queryable binary JSON |
| Small set of labels | `TEXT[]` + GIN index | Lightweight tagging without join table |

## 2. Index Types

Indexes speed reads, slow writes. Add deliberately based on query patterns.

### B-tree (default)

Supports `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `IN`, `IS NULL`, `LIKE 'prefix%'`.

**Composite index rule:** equality columns first, then range/inequality, then ORDER BY columns. The planner uses a leftmost prefix; it cannot skip columns before PG 18 (18+ can skip-scan a low-cardinality leading column, but correct ordering is still preferred). Covering indexes (`INCLUDE`) enable index-only scans (PG 11+).

### GIN — multi-value types (arrays, JSONB, full-text `tsvector`)

Larger and slower to update than B-tree, much faster for containment/overlap/match. Use for any `@>`, `?`, `&&`, or `@@` query. `jsonb_path_ops` variant is smaller but only supports `@>` (no key-existence `?`).

### GiST — ranges, geometry, full-text with ranking

Required for exclusion constraints. Supports range overlap `&&`, containment `<@`, and `ts_rank` ordering.

**GiST vs GIN for full-text:** GIN faster for `@@`; GiST better when you need `ts_rank` ordering and the result set is small. For most apps, GIN.

### BRIN — very large, naturally ordered tables

Stores min/max per range of physical blocks. ~1000x smaller than B-tree on billion-row tables, but only efficient when the indexed column correlates with physical insertion order (timestamps, sequential IDs). Useless on randomly ordered columns (e.g. email).

### Partial & Expression Indexes

- **Partial** — index only relevant rows (smaller, faster) for soft-delete / active subsets (`WHERE deleted_at IS NULL`).
- **Expression** — case-insensitive search + uniqueness (`LOWER(email)`), date truncation (`DATE_TRUNC('month', created_at)`).

### Index Maintenance

- Find unused indexes via `pg_stat_user_indexes` (`idx_scan = 0`, excluding `_pkey`).
- `REINDEX INDEX/TABLE CONCURRENTLY` for non-locking rebuilds (PG 12+).

### Index Type Decision Table

| Query Pattern | Index Type | Example |
|---------------|-----------|---------|
| `=`, `<`, `>`, `BETWEEN`, `ORDER BY` | B-tree | `WHERE status = 'active'` |
| `@>`, `?`, `&&` on JSONB | GIN | `WHERE metadata @> '{"x":1}'` |
| `@>`, `&&` on arrays | GIN | `WHERE tags @> ARRAY['ruby']` |
| `@@` full-text | GIN (or GiST) | `WHERE tsv @@ to_tsquery(...)` |
| Range overlap `&&` | GiST | `WHERE dates && daterange(...)` |
| Geometric containment | GiST | `WHERE point <@ box(...)` |
| Time-series, huge table | BRIN | `WHERE created_at > NOW() - '1d'` |
| Subset of rows | Partial (any type) | `WHERE deleted_at IS NULL` |
| Case-insensitive match | Expression (B-tree) | `WHERE LOWER(email) = ...` |
| Eliminate heap access | Covering (INCLUDE) | `SELECT a, b WHERE c = ...` |

## 3. Query Optimization & EXPLAIN

**Always use `EXPLAIN ANALYZE`, never bare `EXPLAIN`** — estimates can be wildly wrong; only real execution data reveals the bottleneck. Full diagnostic: `EXPLAIN (ANALYZE, BUFFERS, FORMAT YAML)` (PG 18+ includes BUFFERS automatically with ANALYZE).

### Scan Types

- **Seq Scan** — reads whole table. Fine for small tables or when most rows match. If table is large and few rows match → add an index.
- **Index Scan** — index finds rows, heap read for other columns. Good for few rows from a large table.
- **Index Only Scan** — reads index only, never the heap. Fastest; needs all columns in the index (INCLUDE/composite) and a clean visibility map.
- **Bitmap Index/Heap Scan** — medium selectivity, or combining multiple indexes. Used when too many rows for Index Scan but too few for Seq Scan.

### Join Strategies

- **Nested Loop** — for each outer row, scan inner. Best when inner has an index and outer is small.
- **Hash Join** — build hash from smaller side, probe with larger. Best for equijoins with no useful index, tables fitting in `work_mem`.
- **Merge Join** — both sides sorted, merged. Best when both already sorted (index) or very large.

### Common Fixes

- Seq Scan on large table + selective filter → `CREATE INDEX`.
- Estimate vs actual rows wildly different → stale stats → `ANALYZE table`.
- After creating an index, re-run `EXPLAIN ANALYZE` to confirm it's used.

### Scan Type Decision Table

| Scan Type | When Used | Performance |
|-----------|-----------|-------------|
| Seq Scan | No suitable index OR most rows match | O(n) |
| Index Scan | Few rows match, index exists | O(log n + k) |
| Index Only Scan | All columns in index, visibility map clean | O(log n) — fastest |
| Bitmap Index/Heap | Medium selectivity, or combining indexes | O(n × selectivity) |

## 4. Window Functions

Compute across related rows without collapsing them (unlike `GROUP BY`).

- **ROW_NUMBER** — unique sequential per partition. **RANK** — ties share rank, gaps after (1,2,2,4). **DENSE_RANK** — ties share rank, no gaps (1,2,2,3).
- **LAG / LEAD** — previous/next row's value (period-over-period comparisons, gap detection).
- **Running aggregates** — `SUM(x) OVER (PARTITION BY ... ORDER BY ...)`.
- **Percent of total** — `100.0 * x / SUM(x) OVER ()`.
- **Top N per group** — `ROW_NUMBER() OVER (PARTITION BY ...)` in a subquery, filter `WHERE rn <= N`.

### Frame Clauses

- `ROWS BETWEEN n PRECEDING AND CURRENT ROW` — physical row count (last n rows regardless of gaps).
- `RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW` — logical value range (handles gaps correctly).
- Default for `ORDER BY` is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

**Use a window function, not a correlated subquery, for running totals** — the subquery `(SELECT SUM(amount) FROM payments p2 WHERE p2.id <= p1.id)` is O(n²); the window version is a single pass.

## 5. CTEs & Recursive Queries

### MATERIALIZED vs NOT MATERIALIZED (PG 12+)

Pre-PG12 CTEs were always optimization barriers (materialized). PG 12+ defaults non-recursive CTEs to inlinable (`NOT MATERIALIZED`).

- `AS MATERIALIZED` — force materialization (useful when a CTE is referenced multiple times).
- `AS NOT MATERIALIZED` — force inlining so the planner can push predicates (e.g. `WHERE user_id = 42`) into the CTE scan.

### WITH RECURSIVE

For hierarchical traversal (org trees, graphs): anchor query `UNION ALL` recursive term joining back to the CTE. Cycle detection: PG 14+ has native `CYCLE id SET is_cycle USING path`. Pre-14, track manually with an array path and `c.id = ANY(ct.path)` plus `WHERE NOT ct.is_cycle`.

### Writeable CTEs

Chain DML in one statement: `INSERT ... RETURNING` feeds another `INSERT`; `DELETE ... RETURNING` feeds an archive `INSERT` (atomic archive + delete).

## 6. Transaction Isolation & MVCC

### Isolation Levels

- **READ COMMITTED** (default) — each statement sees latest committed data; values can change between statements in the same transaction.
- **REPEATABLE READ** — snapshot taken at first query; reads stay stable. An UPDATE to a row modified concurrently fails: `could not serialize access due to concurrent update`.
- **SERIALIZABLE** — transactions appear to run sequentially; if the result would differ from serial execution → serialization failure. **Must be prepared to retry.**

### Retry Pattern (SERIALIZABLE / REPEATABLE READ)

Loop: BEGIN at the isolation level, do work, COMMIT, break on success; on serialization failure ROLLBACK and retry with backoff.

### MVCC Internals

Each row version has `xmin` (creating txid) and `xmax` (deleting/updating txid; 0 = live). A transaction sees a row when `xmin` is committed before its snapshot AND `xmax` is 0 or not yet committed in its snapshot. This is why DELETEs don't immediately free space — old versions persist until VACUUM removes them.

### Deadlock Prevention

- **Always lock rows in a consistent order** (e.g. by `id ASC`). Two transactions updating ids 1 and 2 in opposite orders will deadlock.
- Use **advisory locks** for app-level locking: `pg_advisory_xact_lock(...)` auto-releases at transaction end.

### Isolation Level Decision Table

| Level | Protects Against | Use When |
|-------|------------------|----------|
| READ COMMITTED | Dirty reads | Default. Most OLTP. |
| REPEATABLE READ | + Non-repeatable & phantom reads | Reports needing a consistent snapshot |
| SERIALIZABLE | + Serialization anomalies (full ACID) | Financial, inventory (must retry on failure) |

## 7. VACUUM & Maintenance

VACUUM: marks dead tuples reusable, updates visibility map (enables index-only scans), updates free space map, and prevents transaction ID wraparound.

### Autovacuum Tuning

Default triggers at `dead_tuples > 50 + 20% of rows` — too late for hot tables (a 1M-row table waits for ~200k dead tuples). Tune per-table via `ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.01, ...)`. For high-write tables: `scale_factor=0` + fixed threshold. Monitor dead-tuple status through `pg_stat_user_tables` (`n_dead_tup`).

### Variants

- `VACUUM` — marks dead tuples reusable; does NOT return disk to the OS.
- `VACUUM ANALYZE` — vacuum + update statistics. Run after bulk INSERT/UPDATE.
- `VACUUM FULL` — rewrites table, reclaims disk, but takes an **AccessExclusive lock (blocks all reads/writes)**. Prefer **pg_repack** (online rewrite, minimal locks).
- `VACUUM VERBOSE` — reports what it did.

### VACUUM Decision Table

| Variant | Lock | Disk Reclaim | When |
|---------|------|-------------|------|
| `VACUUM` | ShareUpdateExclusive (non-blocking) | No — marks reusable | Routine (autovacuum) |
| `VACUUM FULL` | AccessExclusive (blocks all) | Yes — rewrites | Emergency bloat only; prefer pg_repack |
| `VACUUM ANALYZE` | Same as VACUUM | No | After bulk INSERT/UPDATE |
| pg_repack | Minimal | Yes | Scheduled maintenance |

## 8. Connection Management

Each connection costs ~5-10MB RAM + one OS process (postmaster fork) + kernel resources. Default `max_connections = 100`. Monitor via `pg_stat_activity` (group by `state`); set `idle_in_transaction_session_timeout` to prevent connection leaks; terminate long idle-in-transaction backends with `pg_terminate_backend`.

### PgBouncer Modes

| Mode | Behaviour | Prepared Stmts | SET/LISTEN | Best For |
|------|-----------|---------------|-----------|----------|
| Session | Dedicated conn per client session | Yes | Yes | Default, safest |
| Transaction | Conn returned after each transaction | No | No | High-concurrency web apps |
| Statement | Conn returned after each statement | No | No | Simple read-heavy, rare |

Use PgBouncer in **transaction mode** for web apps: 10 instances × 5 threads = 50 client connections sharing ~20 real DB connections. Keep `default_pool_size` modest (e.g. 20), `max_client_conn` high (e.g. 400).

## 9. Security

### Authentication (pg_hba.conf — most specific rules first)

Order rules from most to least specific; end with a `reject` catch-all. Never `trust` (no auth) or `md5` (rainbow-table vulnerable; formally deprecated in PG 18, removal planned) over TCP/IP. Use **scram-sha-256**.

### Role-Based Access Control

Use a dedicated app role with minimal privileges — never the superuser. Grant explicitly and set `ALTER DEFAULT PRIVILEGES` so future tables are covered. Read-only reporting role: `GRANT SELECT` only (+ default privileges).

PG 15+: PUBLIC no longer has CREATE on schema `public` (USAGE remains) — and only in newly created databases; upgraded/restored databases keep prior permissions, so revoke there manually.

### Row-Level Security (multi-tenant)

`ENABLE ROW LEVEL SECURITY` (+ `FORCE` to apply to the table owner) and define a `CREATE POLICY` keyed on `current_setting('app.current_tenant_id')`, set before queries. Per-operation policies: `FOR SELECT ... USING (...)`, `FOR INSERT ... WITH CHECK (...)`.

### SSL/TLS

`SHOW ssl` should be `on`. Connection: `?sslmode=verify-full&sslrootcert=/path/ca.crt`.

| sslmode | Security | Use When |
|---------|----------|----------|
| `disable` | None | Never in production |
| `require` | Encrypted, no verification | Internal network |
| `verify-ca` | Encrypted, CA verified | Trusted CA infra |
| `verify-full` | Encrypted, CA + hostname verified | **Production best practice** |

## 10. Backup & Recovery

### Logical (pg_dump)

`pg_dump -Fc` (custom format: compressed, selective `-t`, `--schema-only`); parallel dumps need the directory format: `pg_dump -Fd -j N`. Restore with `pg_restore -j`. `pg_dumpall` for cluster-wide objects (roles, tablespaces).

### Physical (pg_basebackup) — required for PITR

`pg_basebackup -D ... -Ft -z -P`; PG 17+ supports `--incremental=<manifest>` for delta backups.

### WAL Archiving & PITR

Set `wal_level = replica`, `archive_mode = on`, and an `archive_command` in `postgresql.conf`. PITR: stop PG → restore base backup → set `recovery_target_time` + `restore_command` → create `recovery.signal` → start (replays WAL to target).

### Backup Strategy Table

| Method | Speed | Size | PITR | Cross-Version | Use For |
|--------|-------|------|------|---------------|---------|
| `pg_dump -Fc` | Slow on large | Compressed | No | Yes | Small-medium DBs, migrations |
| `pg_basebackup` | Fast | Full DB | Yes (+WAL) | No | Production backup |
| Incremental (PG 17) | Fastest | Delta only | Yes | No | Large databases |
| pgBackRest | Fast (parallel) | Compressed, dedup | Yes | No | Enterprise production |

**An untested backup is no backup.** Run recovery drills regularly.

## 11. Monitoring & Observability

### pg_stat_statements

Requires `shared_preload_libraries = 'pg_stat_statements'` (restart) + `CREATE EXTENSION`. Query it ordered by `mean_exec_time` (or `total_exec_time` for most time-consuming overall); reset with `pg_stat_statements_reset()`.

### pg_stat_activity

Inspect currently running queries (filter `state='active'`, exclude `pg_backend_pid()`) and blocked queries (join `pg_locks` where `NOT granted` against held locks).

### Table & Index Health

- Tables with many seq scans (missing indexes?) — high `seq_scan` on large `n_live_tup` in `pg_stat_user_tables`.
- Unused indexes — `idx_scan=0` in `pg_stat_user_indexes`, skipping `_pkey` / `_unique`.

### Log Configuration

Key `postgresql.conf` settings: `log_min_duration_statement = 500` (log slow queries), `log_statement = 'ddl'`, `log_checkpoints`, `log_lock_waits`, `log_temp_files = 0`, `log_autovacuum_min_duration = 0`. Enable `auto_explain` (`shared_preload_libraries`) for automatic plan logging of slow queries.

## 12. Replication

### Streaming (Physical)

Byte-for-byte copy; standby replays WAL in near real-time. Primary: `wal_level = replica`, `max_wal_senders`, `wal_keep_size` (or `archive_command`), and a `replication` pg_hba rule. Build the standby with `pg_basebackup -R` (writes `standby.signal` + `primary_conninfo`).

### Logical (PG 10+)

Selective per-table, different schemas allowed, cross-version compatible. `CREATE PUBLICATION` on the primary, `CREATE SUBSCRIPTION` on the subscriber.

### Lag Monitoring & Failover

Monitor lag via `pg_stat_replication` (on primary, `pg_wal_lsn_diff`) or `pg_last_xact_replay_timestamp()` (on standby). Promote a standby with `pg_promote()` (PG 12+). Automated failover tools: Patroni (etcd/consul, most popular), pg_auto_failover, repmgr.

## 13. Schema Design Principles

### Normalization

Default to 3NF — no duplicated data (a copied `user_email`/`user_name` in `orders` goes stale on change). **Denormalize only with reason** (materialized views for reporting, counter columns for hot counts, JSONB for read-heavy semi-structured data) and document WHY.

### Naming Conventions

| Entity | Convention | Example |
|--------|-----------|---------|
| Tables | Plural snake_case | `users`, `order_items` |
| Columns | Singular snake_case | `first_name`, `created_at` |
| Primary key | `id` | `users.id` |
| Foreign key | `singular_table_id` | `orders.user_id` |
| Indexes | `idx_table_columns` | `idx_orders_user_id_created_at` |
| Unique constraints | `uniq_table_columns` | `uniq_users_email` |
| Check constraints | `chk_table_rule` | `chk_orders_total_positive` |
| FK constraints | `fk_table_ref` | `fk_orders_user_id` |

### Constraints-First Design

**NOT NULL by default** — nullable is the exception requiring justification. Every reference needs a foreign key; every domain rule gets a CHECK.

## 14. Modern PostgreSQL (15/16/17/18) Features

### MERGE (PG 15+)

For upsert with complex match/no-match logic. For simple upserts, `INSERT ... ON CONFLICT (col) DO UPDATE SET ... = EXCLUDED.col` is still preferred.

### SQL/JSON Standard

PG 16+: SQL/JSON constructors (`JSON_ARRAY`, `JSON_OBJECT`, `JSON_ARRAYAGG`, `JSON_OBJECTAGG`) and `IS JSON`. PG 17+: `JSON_EXISTS`, `JSON_QUERY`, `JSON_VALUE`, and `JSON_TABLE` (expands a JSON array to rows). The classic `->`/`->>` operators still work and remain widely used.

### Generated Columns

PG 12+ STORED (computed on write, stored on disk — **can be indexed**). PG 18 adds VIRTUAL (computed on read) **and makes it the default** — always write `STORED` explicitly for indexable columns (e.g. a generated `tsvector`); virtual generated columns cannot be indexed. E.g. `full_name TEXT GENERATED ALWAYS AS (first_name || ' ' || last_name) STORED`.

### Other PG 17

- MERGE gains `RETURNING` (with `merge_action()`), `WHEN NOT MATCHED BY SOURCE`, and works on updatable views.
- Incremental `pg_basebackup` (restore with `pg_combinebackup`).
- ~20x memory improvement in VACUUM dead-tuple tracking (automatic on upgrade).
- Logical replication slots survive `pg_upgrade`.

## 15. Anti-Patterns & Production Checklist

### "Don't Do This"

- **CHAR(n)** — padding wastes space → TEXT + CHECK on length.
- **MONEY** — locale-dependent, rounding → NUMERIC(p,s).
- **SERIAL** — implicit sequence, non-standard → IDENTITY.
- **TIMESTAMP WITHOUT TIME ZONE** → TIMESTAMPTZ.
- **`NOT IN (subquery)`** — if any returned value is NULL, the whole query returns ZERO rows → use `NOT EXISTS`.
- **`BETWEEN` for timestamps** — inclusive on both ends, misses same-day times after midnight → half-open range `>= start AND < next`.
- **`SELECT *` in app code** — pulls blobs/unused columns → list needed columns.
- **trust auth over TCP/IP** → scram-sha-256.
- **`max_connections` very high** (each conn = 5-10MB) → PgBouncer + keep it ~100-200.
- **Skipping ANALYZE after bulk load** — stale stats → bad plans → run `ANALYZE table` after `COPY`.
- **Indexes you don't need** — slow every write, waste disk, confuse the planner → only index real query patterns; monitor `pg_stat_user_indexes`.
- **Ignoring bloat** — dead tuples grow the table → slow seq scans → monitor `n_dead_tup`, tune autovacuum, pg_repack.
- **Multiple booleans for mutually-exclusive states** (`is_pending`/`is_shipped`/`is_cancelled` can all be TRUE) → single `status` column with CHECK.

### Production Checklist

| Category | Check |
|----------|-------|
| Data Types | TEXT not VARCHAR; TIMESTAMPTZ not TIMESTAMP; NUMERIC for money; IDENTITY not SERIAL |
| Indexes | Every FK column indexed; unused indexes removed; correct types (GIN for JSONB/arrays, BRIN for time-series) |
| Constraints | NOT NULL by default; FK on every reference; CHECK for domain rules |
| Queries | NOT EXISTS not NOT IN; half-open ranges `>= AND <` not BETWEEN |
| VACUUM | Autovacuum tuned for hot tables; alert when dead_pct > 20% |
| Connections | PgBouncer (transaction mode); max_connections 100-200; idle_in_transaction timeout set |
| Security | scram-sha-256 (never trust/md5 over TCP); app role not superuser; sslmode=verify-full |
| Backups | Automated daily (pg_dump/pgBackRest); WAL archiving for PITR; monthly restore drill |
| Monitoring | pg_stat_statements on; log_min_duration_statement=500; replication lag alert >30s |
| Schema | One status column not multiple booleans; constraints at DB level, not only app validation |
